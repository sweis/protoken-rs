# Code audit, November 2026

Done alongside the move to HMAC-SHA384, ML-DSA, SLH-DSA, and FN-DSA. No way to forge a token
or crash a decoder was found.

## Fixed

| Severity | Finding | Fix |
|---|---|---|
| Medium | `ctutils` 0.4.2 (used by `ml-dsa` and `hmac`) can branch on secrets: RUSTSEC-2026-0385 | Updated to 0.4.7; MSRV is now 1.88 |
| Medium | `inspect` and `verify` printed untrusted claims raw, allowing terminal escape injection; `"a, b"` looked like two scopes | Text is quoted and escaped; JSON is ASCII only |
| Medium | Lean 4.31.0 has kernel soundness bugs (CVE-2026-72844 and others) | Moved to 4.35.0; `make lean` also replays the proofs with `leanchecker` |
| Low | For HMAC keys over 64 bytes, the public key hash was the first 8 bytes of the effective key | Different hash for HMAC; keys capped at the block size |
| Low | Keyed HMAC state was never wiped (`sha2` lacked `zeroize`) | Feature enabled |
| Low | The CLI left secrets in unwiped buffers (base64 output, failed decode attempt) | Zeroizing buffers |
| Low | Public struct fields allowed inconsistent keys | Private fields |
| Low | `Claims` ignored unknown JSON fields, so a misspelled claim was dropped | `deny_unknown_fields` |
| Low | `fn-dsa` accepts corrupted signing keys (see [research-fn-dsa.md](research-fn-dsa.md)) | Portable decoder plus a hash check |
| Low | An ML-DSA public key with `t1 = 0` (for example zero-filled) accepts forgeries from anyone | Rejected on load |
| Testing | `verify_token` used keys unrelated to its seeds, so fuzzing stopped at the key hash check; `max_len` was below the largest token | Reference keys, `max_len`, and a new `verify_untrusted_key` target |
| Testing | No vectors from an independent source | NIST ACVP and RFC 4231 vectors |

## Open

| Item | Notes |
|---|---|
| Update `ml-dsa` to 0.1.2 | Fixes constant-time issues, a panic when rejection sampling is exhausted, and SHAKE state zeroization. Set `ml-dsa = "0.1.2"` in `Cargo.toml`, which also forces a fixed `ctutils` on downstream users, and update both lockfiles. |
| Crafted FN-DSA signing keys | `sign` may not return. Needs an upstream bound or key validation. |
| No domain separation | All three signature schemes take a context string. Using one (for example `protoken`) would stop cross-protocol reuse of a key, but invalidates existing ML-DSA-44 tokens. |
| Deterministic ML-DSA | FIPS 204 prefers hedged signing, which resists fault and side-channel attacks. Switching needs no format change but ends reproducible vectors. |
| No audience check | `verify` returns claims without checking `audience` or `scope`. An `expected_audience` argument would remove a common mistake. |
| Inclusive expiry | A token is valid at `now == expires_at`; JWT rejects it. |
| Token size | SLH-DSA tokens (10-40 KB in base64) exceed common 8 KB HTTP header limits. |
| Broken pipe | The CLI panics if stdout closes early (`\| head`), as any `println!` does. |
| Unaudited dependencies | `ml-dsa`, `slh-dsa` (a release candidate), and `fn-dsa` have no independent audit that we know of. |
